## 1. Глоссарий простыми словами

| Термин | Что это |
|---|---|
| **Cline** | Автономный агент-расширение для VS Code: получает задачу, сам планирует шаги, правит файлы, выполняет команды в терминале, показывает вам чекпоинты для подтверждения |
| **Continue.dev** | Расширение для VS Code/JetBrains: автодополнение кода на лету + чат-панель. Не автономен — просто подсказывает |
| **Approval gate (чекпоинт)** | Момент, когда Cline останавливается и просит вас подтвердить действие, прежде чем продолжить |
| **Plan / Act режим** | В Cline: сначала агент составляет план действий ("Plan"), вы его одобряете, потом он выполняет ("Act") |
| **`.clinerules`** | Файл в корне проекта с инструкциями для Cline: какие правила кодстайла соблюдать, какие команды запускать после правок |
| **Kanban-доска Cline** | Функция для параллельного запуска нескольких задач Cline одновременно (см. Шаг 10 про реальные ограничения) |
| **Манифест** | JSON-файл со списком ТЗ и их зависимостями/используемыми контрактами — источник для графа выполнения |
| **Контекст-пакет** | Небольшой markdown-файл, собранный из контрактов под конкретное ТЗ, чтобы не заставлять агента читать весь репозиторий |
| **Мутационное тестирование** | Способ проверить тесты: в код вносят намеренную "поломку" и смотрят, упадут ли тесты |
| **DeepSeek API** | Облачный API DeepSeek (`api.deepseek.com`), совместимый по формату с OpenAI. Используется как единый провайдер моделей и для Cline, и для Continue.dev |
| **deepseek-v4-flash** | Быстрая и дешёвая модель DeepSeek — годится для автодополнения и несложных ТЗ |
| **deepseek-v4-pro** | Более мощная модель DeepSeek — для сложных агентных задач и критичной логики |

## 2. Роли инструментов: кто за что отвечает

```
┌────────────────────┐     ┌────────────────────┐
│   Continue.dev      │     │       Cline         │
│  (не автономен)      │     │    (автономен)       │
├────────────────────┤     ├────────────────────┤
│ • Автодополнение     │     │ • Выполняет целое ТЗ │
│   на лету            │     │   от начала до конца │
│ • Быстрый чат         │     │ • Сам запускает      │
│   по коду             │     │   тесты/линтеры      │
│ • Ручные мелкие       │     │ • Сам чинит ошибки    │
│   правки               │     │   по выводу терминала│
└────────────────────┘     └────────────────────┘
        │                           │
        └──────────┬────────────────┘
                    ▼
         Модель через DeepSeek API
     (deepseek-v4-pro — агент и чат,
      deepseek-v4-flash — автодополнение)
```

> 💡 **Почему две модели, а не одна на всё.** В отличие от локальной установки, где смена модели стоит времени на перезагрузку весов, облачный API DeepSeek обслуживает разные модели параллельно и мгновенно — переключение между ними ничего не стоит. Поэтому здесь, наоборот, имеет смысл развести роли: `deepseek-v4-flash` — для инлайн-автодополнения (там задержка критичнее качества), `deepseek-v4-pro` — для чата и агентных задач Cline (там важнее качество рассуждений). Если хотите максимально просто — можно временно использовать `deepseek-v4-pro` везде, а `flash` подключить позже, если автодополнение будет ощущаться медленным.

**Простое правило:** «допиши строчку / подскажи прямо сейчас» — это Continue. «Вот целое ТЗ, реализуй метод и тесты» — это Cline.

## 3. Шаг 1. Получение доступа к DeepSeek API

Никакого локального железа и VRAM здесь не нужно — модели считаются на серверах DeepSeek, а вы платите по токенам.

1. Зарегистрируйтесь на [platform.deepseek.com](https://platform.deepseek.com), пополните баланс и создайте API-ключ (`sk-...`).
2. Сохраните ключ в переменную окружения, чтобы не хранить его в конфигах открытым текстом:

```bash
export DEEPSEEK_API_KEY="sk-ваш-ключ"
```

3. Базовый URL API: `https://api.deepseek.com` (формат запросов — OpenAI-совместимый).

### Какие модели использовать

> ⚠️ Модели `deepseek-chat` и `deepseek-reasoner` объявлены устаревшими (депрекация — 24 июля 2026). Используйте актуальные названия:

| Модель | Для чего |
|---|---|
| `deepseek-v4-pro` | Агентные задачи в Cline, сложная логика, чат в Continue |
| `deepseek-v4-flash` | Автодополнение в Continue, простые/быстрые ТЗ |

Проверить актуальный список моделей и цены можно на [странице моделей DeepSeek](https://api-docs.deepseek.com/quick_start/pricing) — API развивается быстро, названия моделей и тарифы стоит сверять перед стартом проекта.

### Embeddings: чего в DeepSeek API нет

У DeepSeek нет официального endpoint для эмбеддингов (только чат-модели). Для поиска по репозиторию (RAG) в Continue.dev понадобится отдельный источник эмбеддингов. Самый простой вариант — оставить его локальным, не трогая облако: модель эмбеддингов лёгкая (не сравнить с агентными моделями DeepSeek) и прекрасно работает даже на CPU.

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull nomic-embed-text
```

Если не хотите держать Ollama даже ради этого — можно подключить любой облачный embeddings-провайдер (например, OpenAI `text-embedding-3-small` или Voyage AI) через `embeddingsProvider` в Continue; конфигурация аналогична, меняются только `provider`/`apiKey`.

> 💡 Если RAG-поиск по репозиторию не критичен на старте — этот шаг можно пропустить и вернуться к нему позже: без него контекст-пакеты (Шаг 7) всё равно продолжат строиться через `ast`/`sqlglot`, просто без дополнительного полнотекстового поиска по кодовой базе.

## 4. Шаг 2. Настройка Continue.dev

Continue.dev поддерживает DeepSeek как встроенного провайдера — не нужен даже `apiBase`, только `provider: deepseek`.

```json
{
  "models": [
    {
      "title": "DeepSeek V4 Pro",
      "provider": "deepseek",
      "model": "deepseek-v4-pro",
      "apiKey": "${env:DEEPSEEK_API_KEY}"
    }
  ],
  "tabAutocompleteModel": {
    "title": "DeepSeek V4 Flash",
    "provider": "deepseek",
    "model": "deepseek-v4-flash",
    "apiKey": "${env:DEEPSEEK_API_KEY}"
  },
  "embeddingsProvider": {
    "provider": "ollama",
    "model": "nomic-embed-text"
  }
}
```

- **`deepseek-v4-pro`** — чат-панель для вопросов и мелких правок, где важнее качество.
- **`deepseek-v4-flash`** — автодополнение во время набора кода, где важнее скорость отклика.
- **`embeddingsProvider`** остаётся на локальной Ollama (Шаг 1) — поиск похожих фрагментов по репозиторию сверх контекст-пакета, у DeepSeek такого API нет.

> ⚠️ Если у используемой версии Continue провайдер `deepseek` ещё не подхватывает актуальные названия моделей — используйте универсальный OpenAI-совместимый провайдер вместо него: `"provider": "openai"`, `"apiBase": "https://api.deepseek.com"`, `"model": "deepseek-v4-pro"` (или `flash`). Формат запросов идентичен.

> 💡 Не храните ключ в config.json напрямую в общем репозитории — `${env:DEEPSEEK_API_KEY}` подставляет значение из переменной окружения, заданной на Шаге 1.

## 5. Шаг 3. Настройка Cline

1. Установите расширение **Cline** (VS Code или JetBrains).
2. Настройте провайдер одним из двух способов:

   **Способ А — встроенный провайдер DeepSeek** (проще, но может отставать от свежих моделей DeepSeek):
   - **API Provider:** `DeepSeek`
   - **DeepSeek API Key:** ваш ключ с Шага 1
   - **Model:** `deepseek-v4-pro` (если модель ещё не появилась в выпадающем списке — используйте способ Б)

   **Способ Б — OpenAI Compatible** (надёжнее в переходный период, когда Cline ещё не обновил список моделей DeepSeek):
   - **API Provider:** `OpenAI Compatible`
   - **Base URL:** `https://api.deepseek.com`
   - **Model ID:** `deepseek-v4-pro`
   - **API Key:** ваш ключ с Шага 1

3. Включите **Plan/Act режим**.
4. Для старта держите **все действия под ручным подтверждением** — так вы увидите, что и как Cline меняет, прежде чем разрешать авто-подтверждение безопасных операций (чтение файлов, запуск тестов).

> 💡 Держите `deepseek-v4-pro` моделью по умолчанию для агентных задач Cline — экономия на переключении на `flash` того не стоит, если речь о полноценном ТЗ с планированием и правкой кода. `flash` имеет смысл оставить только за автодополнением в Continue (Шаг 2).

## 6. Шаг 4. Архитектура → Контракты → ТЗ

```
Архитектура (общая схема, 1 раз)
        │
        ▼
Контракты (общие таблицы БД, типы данных, коды ошибок)
        │
        ▼
Декомпозиция (список маленьких независимых ТЗ)
        │
        ▼
Самодостаточное ТЗ на каждую задачу
        │
        ▼
   Задача для Cline
```

### Пример: `architecture.md` для проекта Snake

Это документ верхнего уровня — пишется один раз (человеком или через Cline в чат-режиме, не как ТЗ), и на него ссылаются контракты и декомпозиция, но сам он **не передаётся целиком** ни в контекст-пакет, ни в задачи Cline — только его выжимка, если понадобится.

```markdown
# Multiplayer Snake — Архитектура

## Назначение
Сетевая многопользовательская змейка: несколько игроков подключаются
к одной партии, видят синхронное состояние поля, соревнуются за очки.
После игры результат попадает в рейтинг, партию можно пересмотреть в реплее.

## Стек
- Клиент: Python 3.12 + pygame
- Сервер: FastAPI + WebSocket
- БД: SQLite (для старта; миграция на PostgreSQL не планируется в MVP)
- Валидация данных: Pydantic
- Тесты: pytest + Hypothesis + mutmut

## Слои
```
Client (pygame)
      │  WebSocket
      ▼
Server (FastAPI)
      │
      ▼
Service-слой (game, auth, leaderboard, replay — чистая логика)
      │
      ▼
Repository-слой (доступ к SQLite)
      │
      ▼
SQLite
```

## Модули и их ответственность

| Модуль | Отвечает за | НЕ отвечает за |
|---|---|---|
| `auth` | Регистрация, логин, выдача JWT | Игровую логику |
| `game` | Правила игры: шаг змейки, еда, коллизии | Сеть, БД — модуль полностью "чистый" |
| `net` | WebSocket-хаб: приём команд, рассылка состояния | Правила игры — только транспорт |
| `leaderboard` | Агрегация очков, топ игроков | Запись очков (это делает `game` при завершении партии) |
| `replay` | Запись тиков партии, воспроизведение | Ничего игрового — только сериализация состояний |

## Игровой цикл
- Тик сервера — раз в 100 мс (10 тиков/сек).
- На каждом тике: `net` собирает накопленные команды игроков → передаёт в `game` →
  `game` считает новое состояние → `net` рассылает `GameState` всем клиентам.
- Максимум игроков в одной партии: 4 (см. `contracts/config.py`).

## Принципы, которые нельзя нарушать при декомпозиции на ТЗ
1. **`game` — чистые функции, без сайд-эффектов.** Ни сети, ни БД внутри модуля.
   Это то, что делает `game`-модуль по-настоящему тестируемым юнит-тестами.
2. **`net` — только транспорт.** Вся игровая логика живёт в `game`; `net` её вызывает,
   но не дублирует и не переопределяет.
3. **Все контракты — в `/contracts`.** Ни один модуль не описывает свои типы/ошибки
   локально, если они используются больше чем в одном месте.
4. **Граница модуля = кандидат на интеграционное ТЗ.** Взаимодействие `game` ↔ `net`
   и `game` ↔ `replay` тестируется отдельно от юнитов внутри модулей (см. Шаг 11).

## Что осознанно вынесено за скобки MVP
- Реконнект игрока после разрыва соединения — не реализуется в первой версии.
- Масштабирование на несколько серверов (сейчас один процесс = одна партия).
- Античит — не рассматривается, потому что игра казуальная, без денег.

## Внешние зависимости
Нет. Проект не использует сторонние API — упрощает и тестирование, и деплой.
```

**Что делает архитектуру полезной для дальнейшей декомпозиции:**
- Таблица "модуль → ответственность" — прямой источник для `module` в манифесте задач.
- Явные принципы ("game — чистые функции", "net — только транспорт") — то, что стоит продублировать в `.clinerules`, чтобы Cline их не нарушал при реализации отдельных ТЗ.
- Раздел "что вынесено за скобки" — защищает от ситуации, когда Cline "по инициативе" начинает реализовывать реконнект или античит внутри несвязанного ТЗ, потому что решил, что это часть проекта.
- Раздел про игровой цикл — источник для интеграционных ТЗ (Шаг 11): именно здесь описана граница `net` ↔ `game`, которую юнит-тесты не покрывают.



```
/contracts
  ├── db_schema.sql
  ├── api_openapi.yaml
  ├── types.py
  ├── errors.py
  └── config.py

/tasks
  ├── _manifest.json
  └── <task_id>.md
```

### Формат ТЗ

```markdown
# ТЗ: OrderService.create_order

## Контекст
- Модуль: orders
- Зависит от: UserRepository, PaymentClient
- Таблицы: orders, order_items

## Задача
Создать метод create_order(user_id, items) → Order

## Контракт
- Вход: CreateOrderRequest
- Выход: Order
- Ошибки: UserNotFound, EmptyCart, PaymentFailed

## Требования
1. Валидация: пользователь существует, корзина не пуста
2. Резервирование товара
3. Вызов оплаты
4. Откат при ошибке платежа

## Тесты
- Happy path
- Пустая корзина
- Несуществующий пользователь
- Ошибка платежа
```

## 7. Шаг 5. Пример проекта: Multiplayer Snake

**Стек:** Python 3.12, pygame (клиент), FastAPI + WebSocket (сервер), SQLite, Pydantic.
**Модули:** `auth`, `game`, `net`, `leaderboard`, `replay`.

### `contracts/types.py`

```python
from pydantic import BaseModel, Field
from typing import Literal
from datetime import datetime

class Point(BaseModel):
    x: int
    y: int

class Snake(BaseModel):
    user_id: int
    body: list[Point]  # голова = body[0]
    direction: Literal["up", "down", "left", "right"]
    alive: bool = True

class GameState(BaseModel):
    tick: int
    snakes: list[Snake]
    food: list[Point]
    grid_size: int = 40

class DirectionChange(BaseModel):
    direction: Literal["up", "down", "left", "right"]
```

### `contracts/errors.py`

```python
class AppError(Exception):
    code: str = "APP_ERROR"
    message: str = "Application error"

class InvalidDirection(AppError):
    code = "INVALID_DIRECTION"
    message = "Cannot reverse direction"
```

### `tasks/_manifest.json` (фрагмент)

```json
{
  "tasks": [
    {
      "id": "game_snake_step",
      "module": "game",
      "depends_on": [],
      "uses_types": ["Point", "Snake", "DirectionChange"],
      "uses_tables": [],
      "uses_errors": ["InvalidDirection"],
      "priority": 1
    },
    {
      "id": "game_check_collision",
      "module": "game",
      "depends_on": ["game_snake_step"],
      "uses_types": ["Point", "Snake", "GameState"],
      "uses_tables": [],
      "uses_errors": [],
      "priority": 2
    }
  ]
}
```

### `tasks/game_snake_step.md`

```markdown
# ТЗ: game.snake_step

## Задача
Реализовать `snake_step(snake: Snake, change: DirectionChange | None) -> Snake`.

1. Если `change` передан и не противоположен текущему направлению — обновить его.
2. Иначе — оставить текущее направление.
3. Сдвинуть тело: новая голова = текущая голова + вектор направления.
4. Хвост отрезать (длина сохраняется).

## Контракт
- Вход: Snake, DirectionChange | None
- Выход: Snake (новая, без изменения исходной)
- Ошибки: InvalidDirection — если попытка развернуться на 180°

## Тесты
- Обычное движение вправо
- Смена направления на перпендикулярное
- Попытка разворота на 180° → InvalidDirection
- change=None → движение в текущем направлении
- Проверка, что вход не изменился
```

## 9. Шаг 7. Сборка контекст-пакета: без хрупкого регэкспа

Смысл среза контекста (только нужные типы/таблицы/ошибки под конкретное ТЗ) остаётся полезным: без него агент читает весь репозиторий и тратит токены впустую на слабом локальном железе.

Но у наивной реализации через `re.split` по строке `"class "` или `"CREATE TABLE"` есть реальная проблема: она ломается на вложенных классах, многострочных значениях, декораторах, комментариях со словом `class` внутри строки — и, что хуже всего, **ломается тихо**: скрипт не упадёт с ошибкой, просто отдаст неполный или обрезанный кусок контекста, и вы не заметите этого, пока не увидите, что Cline "почему-то" не знает про какой-то тип.

Правильный инструмент для среза — не регэксп, а настоящий парсер: `ast` для Python-контрактов и `sqlglot` для SQL-схемы.

```bash
pip install sqlglot
```

```python
# tools/build_context_pack.py
import ast
import json
from pathlib import Path

import sqlglot
from sqlglot import exp

ROOT = Path(__file__).parent.parent
CONTRACTS = ROOT / "contracts"
TASKS = ROOT / "tasks"
CONTEXT_OUT = TASKS / "_context"


def load_manifest() -> dict:
    return json.loads((TASKS / "_manifest.json").read_text())


def extract_python_classes(source: str, names: list[str]) -> str:
    """Через ast, а не регэксп: устойчиво к декораторам, вложенности, комментариям."""
    if not names:
        return ""
    tree = ast.parse(source)
    lines = source.splitlines()
    keep = []
    for node in ast.walk(tree):
        if isinstance(node, ast.ClassDef) and node.name in names:
            # ast даёт точные номера строк начала/конца блока,
            # включая декораторы — регэксп такого не умеет.
            start = min(d.lineno for d in node.decorator_list) if node.decorator_list else node.lineno
            end = node.end_lineno
            keep.append("\n".join(lines[start - 1:end]))
    return "\n\n".join(keep)


def extract_sql_tables(source: str, names: list[str]) -> str:
    """Через sqlglot: понимает SQL-синтаксис, а не просто ищет подстроку."""
    if not names:
        return ""
    statements = sqlglot.parse(source)
    keep = []
    for stmt in statements:
        if isinstance(stmt, exp.Create):
            table = stmt.this
            table_name = table.this.name if hasattr(table, "this") else None
            if table_name in names:
                keep.append(stmt.sql(pretty=True) + ";")
    return "\n\n".join(keep)


def build_context_pack(task_id: str) -> Path:
    manifest = load_manifest()
    task = next(t for t in manifest["tasks"] if t["id"] == task_id)

    types_src = (CONTRACTS / "types.py").read_text()
    schema_src = (CONTRACTS / "db_schema.sql").read_text()
    errors_src = (CONTRACTS / "errors.py").read_text()

    types_slice = extract_python_classes(types_src, task["uses_types"])
    tables_slice = extract_sql_tables(schema_src, task["uses_tables"])
    errors_slice = extract_python_classes(errors_src, task["uses_errors"])

    content = f"""# Контекст-пакет для {task_id}

## Зависит от (уже должно быть реализовано)
{', '.join(task['depends_on']) or '— нет'}

## Релевантные типы (contracts/types.py)
```python
{types_slice}
```

## Релевантные таблицы (contracts/db_schema.sql)
```sql
{tables_slice}
```

## Релевантные ошибки (contracts/errors.py)
```python
{errors_slice}
```
"""
    CONTEXT_OUT.mkdir(exist_ok=True)
    out_path = CONTEXT_OUT / f"{task_id}.context.md"
    out_path.write_text(content)
    return out_path


if __name__ == "__main__":
    import sys
    task_id = sys.argv[1] if len(sys.argv) > 1 else "game_snake_step"
    path = build_context_pack(task_id)
    print(f"Контекст-пакет сохранён: {path}")
```

Запуск:

```bash
python tools/build_context_pack.py game_snake_step
```

> 💡 Даже с `ast`/`sqlglot` стоит один раз глазами свериться, что контекст-пакет получился полным — особенно на первых прогонах, пока вы не убедились, что парсер правильно понимает ваш конкретный стиль кода в контрактах.

**Как использовать с Cline:** откройте задачу, приложите через `@`-упоминание `tasks/game_snake_step.md` и `tasks/_context/game_snake_step.context.md`, попросите реализовать ТЗ.

## 10. Шаг 8. Манифест и граф зависимостей: где он расходится с реальностью

`_manifest.json` — сам по себе ещё один контракт, который тоже может протухнуть: кто-то добавил новый тип в `types.py`, но забыл обновить `uses_types` в манифесте, или переименовал задачу в `_manifest.json`, но не переименовал файл ТЗ. Такое рассогласование не выдаст ошибку явно — просто контекст-пакет соберётся неполным, а граф зависимостей построится по устаревшим данным.

Поэтому перед сборкой контекста и перед построением графа стоит явно проверять манифест, а не доверять ему вслепую:

```python
# tools/validate_manifest.py
import ast
import json
import re
from pathlib import Path

ROOT = Path(__file__).parent.parent
CONTRACTS = ROOT / "contracts"
TASKS = ROOT / "tasks"


def get_class_names(path: Path) -> set[str]:
    tree = ast.parse(path.read_text())
    return {n.name for n in ast.walk(tree) if isinstance(n, ast.ClassDef)}


def get_table_names(path: Path) -> set[str]:
    return set(re.findall(r"CREATE TABLE (\w+)", path.read_text()))


def main() -> int:
    manifest = json.loads((TASKS / "_manifest.json").read_text())
    known_ids = {t["id"] for t in manifest["tasks"]}
    known_types = get_class_names(CONTRACTS / "types.py")
    known_errors = get_class_names(CONTRACTS / "errors.py")
    known_tables = get_table_names(CONTRACTS / "db_schema.sql")

    problems = []

    for task in manifest["tasks"]:
        task_id = task["id"]

        # 1. Файл ТЗ существует?
        if not (TASKS / f"{task_id}.md").exists():
            problems.append(f"[{task_id}] нет файла tasks/{task_id}.md")

        # 2. Зависимости ссылаются на существующие задачи?
        for dep in task["depends_on"]:
            if dep not in known_ids:
                problems.append(f"[{task_id}] зависит от несуществующей задачи '{dep}'")

        # 3. Используемые типы/ошибки/таблицы реально существуют в контрактах?
        for t in task.get("uses_types", []):
            if t not in known_types:
                problems.append(f"[{task_id}] тип '{t}' не найден в contracts/types.py")
        for e in task.get("uses_errors", []):
            if e not in known_errors:
                problems.append(f"[{task_id}] ошибка '{e}' не найдена в contracts/errors.py")
        for tbl in task.get("uses_tables", []):
            if tbl not in known_tables:
                problems.append(f"[{task_id}] таблица '{tbl}' не найдена в contracts/db_schema.sql")

    if problems:
        print("❌ Манифест рассинхронизирован с реальными файлами:")
        for p in problems:
            print(f"  - {p}")
        return 1

    print("✅ Манифест синхронизирован с контрактами и файлами ТЗ")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**Правило:** запускайте `validate_manifest.py` перед `build_context_pack.py` и перед построением графа — если манифест разъехался с реальностью, лучше узнать об этом до того, как Cline получит неполный или пустой контекст, а не после.

### Граф зависимостей (не меняется в сравнении с идеей)

```python
# tools/dep_graph.py
import json
from pathlib import Path
import networkx as nx

ROOT = Path(__file__).parent.parent
TASKS = ROOT / "tasks"


def load_manifest() -> dict:
    return json.loads((TASKS / "_manifest.json").read_text())


def build_graph() -> nx.DiGraph:
    manifest = load_manifest()
    g = nx.DiGraph()
    for task in manifest["tasks"]:
        g.add_node(task["id"], priority=task.get("priority", 99))
        for dep in task["depends_on"]:
            g.add_edge(task["id"], dep)

    if not nx.is_directed_acyclic_graph(g):
        raise ValueError(f"Циклические зависимости: {list(nx.simple_cycles(g))}")
    return g


def execution_order() -> list[list[str]]:
    g = build_graph()
    levels, remaining, done = [], set(g.nodes), set()

    while remaining:
        ready = {n for n in remaining if all(dep in done for dep in g.successors(n))}
        if not ready:
            raise ValueError("Тупик: невозможно продолжить")
        level = sorted(ready, key=lambda n: g.nodes[n]["priority"])
        levels.append(level)
        done |= ready
        remaining -= ready

    return levels


if __name__ == "__main__":
    for i, level in enumerate(execution_order(), 1):
        print(f"Уровень {i}: {', '.join(level)}")
```

## 12. Шаг 10. Параллелизм и рейт-лимиты облачного API: честные ожидания

У Cline есть Kanban-доска для параллельного запуска нескольких задач — ближайший встроенный аналог идеи "уровень графа = можно генерировать одновременно". В отличие от локальной GPU, DeepSeek API действительно способен считать несколько запросов параллельно на своей стороне — узкое место здесь другое.

**Ограничение теперь — не железо, а рейт-лимиты и бюджет.** У DeepSeek API, как у любого облачного провайдера, есть лимиты на число запросов и токенов в минуту (конкретные цифры зависят от вашего тарифа — сверяйтесь с [текущей документацией DeepSeek](https://api-docs.deepseek.com)), а также параллельные агентные задачи Cline легко тратят токены пропорционально числу параллельных запусков.

Практический вывод:
- **Kanban реально ускоряет выполнение по времени** на облачном API — в отличие от локальной GPU, здесь параллельные ТЗ действительно считаются одновременно, а не по очереди.
- **Следите за рейт-лимитами.** Если несколько параллельных задач Cline начинают падать с ошибками `429 Too Many Requests` — это сигнал снизить число одновременных задач на Kanban-доске, а не баг в конфигурации.
- **Следите за бюджетом.** Параллелизм умножает скорость трат токенов линейно: 4 параллельных ТЗ на Kanban-доске сожгут бюджет примерно в 4 раза быстрее, чем одно и то же ТЗ по очереди. Перед тем как распараллеливать целый уровень графа зависимостей, прикиньте стоимость по [текущим ценам DeepSeek](https://api-docs.deepseek.com/quick_start/pricing).
- Для дорогих или долгих цепочек ТЗ разумно распараллеливать не весь уровень графа сразу, а частями — так проще заметить, что где-то пошло не так, до того как это размножилось на все параллельные задачи.

## 13. Шаг 11. Гранулярность ТЗ: что декомпозиция не ловит

Декомпозиция на уровне "одна функция = одно ТЗ" (как `game_snake_step` или `leaderboard_top`) хорошо ловит **юнит-баги**: неправильную формулу, забытую проверку границы, неверный тип. Но у неё есть системный пробел — она почти ничего не говорит о том, что происходит **на стыке модулей**.

В примере со змейкой реальные баги скорее всего будут не внутри чистой функции `snake_step`, а в:
- порядке обработки тика между `game` и `net` (кто-то из игроков получил состояние на 100 мс позже другого);
- гонках состояния при одновременном подключении нескольких игроков;
- рассинхронизации протокола, когда `ws_protocol.md` обновили, а клиент и сервер поняли изменение по-разному.

Ни `.clinerules`, ни контекст-пакет, ни мутационное тестирование этого не поймают — они работают в границах одного ТЗ, а проблема находится между ТЗ.

### Что с этим делать

Добавьте в манифест отдельный **тип** задач — интеграционные ТЗ, которые не привязаны к одному модулю:

```json
{
  "id": "integration_two_players_sync",
  "module": "integration",
  "type": "integration",
  "depends_on": ["game_snake_step", "net_broadcast_state"],
  "uses_types": ["GameState", "Snake"],
  "uses_tables": [],
  "uses_errors": [],
  "priority": 4
}
```

И явное ТЗ для него:

```markdown
# ТЗ (интеграционное): integration.two_players_sync

## Задача
Проверить, что при подключении двух игроков одновременно оба получают
согласованное состояние на каждом тике — без гонок и рассинхронизации.

## Сценарий теста
1. Поднять сервер в тестовом режиме.
2. Подключить двух клиентов почти одновременно (разница < 10мс).
3. Отправить оба направления в один тик.
4. Проверить, что оба клиента получили ОДИНАКОВЫЙ GameState на каждом тике.

## Важно
Это НЕ юнит-тест. Тестируется взаимодействие game + net, а не отдельная функция.
```

**Правило:** запускайте интеграционные ТЗ отдельно, после того как связанные модульные ТЗ уже прошли проверку — и обязательно после каждого уровня графа, который затрагивает границу между модулями, а не только в самом конце проекта.

## 14. Шаг 12. Проверка качества и риск ложной уверенности

`.clinerules` заставляет Cline запускать `ruff`/`mypy`/`pytest` после каждой задачи. Отдельный скрипт `validate.py` нужен как **независимый финальный контроль**, а не дублирование того, что агент "как бы" уже сделал:

```python
# tools/validate.py
import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).parent.parent
SRC = ROOT / "src"


def run(cmd: list[str]) -> tuple[int, str]:
    p = subprocess.run(cmd, capture_output=True, text=True, cwd=SRC)
    return p.returncode, p.stdout + p.stderr


def main() -> int:
    print("== ruff ==")
    _, out = run(["ruff", "check", "."])
    print(out or "  OK")

    print("\n== mypy ==")
    _, out = run(["mypy", "--ignore-missing-imports", "."])
    print(out or "  OK")

    print("\n== pytest ==")
    code, out = run(["pytest", "-q"])
    print(out or "  OK")
    if code != 0:
        print("  ❌ тесты упали")
        return 1

    print("\n== mutmut (запустите вручную: mutmut run) ==")
    print("  Цель: mutation score выше 80%")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

### Почему "все проверки зелёные" — это не то же самое, что "код правильный"

Здесь главный риск не в том, что тесты не запустятся, а в том, что **линт прошёл, mypy прошёл, pytest прошёл, mutation score выше 80% — и всё это может дружно подтверждать одну и ту же неверную интерпретацию требований**, если код и тесты писал один и тот же агент по одному и тому же (возможно, неточно понятому) ТЗ.

Мутационное тестирование решает только одну конкретную проблему — "тесты ничего не проверяют". Оно **не решает** другую: "тесты проверяют не то, что нужно бизнесу". Пример: если в ТЗ на `leaderboard_top` неправильно понята сортировка при равных очках, а тесты написаны в соответствии с этим же неверным пониманием — все проверки пройдут зелёным, при этом фича будет работать не так, как задумано.

Что реально снижает этот риск:

1. **Разные модели/сессии для кода и тестов.** Если возможно — пусть тесты пишет отдельная сессия Cline (или другая модель через смену провайдера), а не тот же контекст, что писал реализацию. Свежий "взгляд" с большей вероятностью заметит рассогласование с ТЗ, а не просто подтвердит уже написанный код.
2. **TDD-порядок, где это возможно.** Формулируйте ожидаемое поведение (тесты или хотя бы описание сценариев) до того, как Cline увидит реализацию — так меньше шанс, что тест "подгонится" под баг.
3. **Обязательное человеческое ревью для критичной логики** — не как опциональный шаг "если будет время", а как явный чекпоинт в процессе, который нельзя пропустить для бизнес-логики, безопасности и любых денежных операций. Зелёные проверки — это фильтр, отсекающий явный мусор, а не подтверждение правильности замысла.

## 15. Шаг 13. Fix-loop — встроен, а не самописный

У Cline это часть агентного цикла:

1. Cline запускает `pytest` (прописано в `.clinerules`).
2. Видит в терминале реальный вывод ошибки — без парсинга регэкспами, напрямую.
3. Сам решает, какой файл и как править.
4. Показывает вам diff на чекпоинте.
5. После вашего подтверждения — перезапускает тесты.

**Ограничивайте число итераций здравым смыслом:** если после 3 попыток Cline не может починить тест — это сигнал, что дело не в мелкой ошибке, а в неверном понимании ТЗ. Остановитесь и переформулируйте задачу, а не продолжайте попытки.

## 16. Итоговый рабочий цикл одного ТЗ

```
1. python tools/validate_manifest.py           (манифест не разъехался с контрактами?)
        │
        ▼
2. python tools/build_context_pack.py <task_id>
        │
        ▼
3. Открыть задачу в Cline, приложить .md ТЗ + .context.md
        │
        ▼
4. Проверить план Cline (Plan-режим)
        │
        ▼
5. Одобрить → Cline пишет код + тесты, сам гоняет ruff/mypy/pytest
        │
        ▼
6. Если тесты упали → Cline чинит сам (максимум 2-3 попытки)
        │
        ▼
7. Независимый validate.py + mutmut run
        │
        ▼
8. Интеграционное ТЗ, если задача затрагивает границу модулей
        │
        ▼
9. Обязательное ревью человеком для критичной логики → git commit
```

## 17. Частые ошибки новичков

| Ошибка | Почему это плохо | Как избежать |
|---|---|---|
| Давать Cline ТЗ без контекст-пакета | Агент читает весь репозиторий, тратит токены, путается | Всегда прикладывайте `.context.md` |
| Доверять регэксп-парсингу контрактов вслепую | Тихо теряются или обрезаются нужные типы/таблицы | Используйте `ast`/`sqlglot`, сверяйте результат глазами на первых прогонах |
| Не проверять манифест | Граф и контекст строятся по устаревшим данным без явной ошибки | Гоняйте `validate_manifest.py` перед каждым циклом |
| Считать декомпозицию "одна функция = одно ТЗ" достаточной | Баги на стыке модулей (гонки, протокол) остаются незамеченными | Добавляйте отдельные интеграционные ТЗ |
| Верить "все проверки зелёные" как доказательству правильности | Код и тесты могли подтвердить одно и то же неверное понимание ТЗ | Разные сессии для кода/тестов, обязательное ревью критичной логики |
| Распараллеливать весь уровень графа не глядя на рейт-лимиты и бюджет | Запросы падают с `429`, либо токены сгорают в несколько раз быстрее ожидаемого | Проверяйте лимиты тарифа и прикидывайте стоимость перед распараллеливанием (Шаг 10) |
| Продолжать fix-loop бесконечно при непонятной ошибке | Модель может начать хаотично менять код | После 3 неудачных попыток — остановитесь и переформулируйте ТЗ |

## 19. Куда развиваться дальше

1. **MCP-сервер поверх контрактов**, который сам отдаёт Cline нужный срез контекста по запросу — вместо ручного прикладывания `.context.md`.
2. **Гибридный роутинг между моделями DeepSeek:** несложные и повторяющиеся ТЗ — на `deepseek-v4-flash` (дешевле и быстрее), сложные/критичные — на `deepseek-v4-pro`, переключением модели в настройках Cline под конкретную задачу.
3. **CI-проверка манифеста и качества** на каждое изменение в `contracts/` или `tasks/`, чтобы рассинхронизация и падение mutation score ловились автоматически, а не в момент, когда вы случайно это заметите.
4. **Библиотека интеграционных сценариев**, растущая параллельно с модульными ТЗ, а не добавляемая "под конец" проекта.
