# ТЗ 02 — Key Generation

**Контракт:** `contracts/02_key_generation.md`
**Зависимости:** нет (чистые функции, БД не трогают)
**Файлы:** `src/core/keys/generate.py`, `tests/core/keys/test_generate.py`

## Задача

Реализовать все функции из контракта: `new_vless_uuid`, `new_reality_short_id`, `new_reality_keypair`,
`new_password`, `new_naive_username`. Для `new_reality_keypair` — выбрать один способ (рекомендация:
`cryptography.hazmat.primitives.asymmetric.x25519`, чтобы не зависеть от наличия бинарника sing-box
на машине, где гоняются тесты) и явно задокументировать выбор в docstring.

## Критерии приёмки

- [ ] `new_vless_uuid()` — валидный UUID v4 (тест через `uuid.UUID(value, version=4)`).
- [ ] `new_reality_short_id()` — ровно 8 hex-символов, `[0-9a-f]{8}`.
- [ ] `new_reality_keypair()` — возвращает пару непустых base64url-строк без padding (`=`),
      приватный и публичный ключ математически связаны (тест: из приватного восстановить публичный
      и сравнить, либо доверять корректности библиотеки — минимум проверить, что ключи разные
      при двух последовательных вызовах).
- [ ] `new_password(length=24)` — длина строки соответствует ожиданиям URL-safe кодирования
      (`secrets.token_urlsafe` возвращает не ровно `length` символов, а ~`4/3*length/... ` —
      явно решить в реализации, что параметр значит: байты энтропии или итоговую длину строки,
      и задокументировать).
- [ ] `new_naive_username("Вася")` → латиница, `[a-z0-9_]{3,32}`, при коллизии с `existing={"vasya"}`
      возвращает `"vasya-2"`.
- [ ] Два последовательных вызова любой функции дают разные значения (кроме вырожденных случаев).
- [ ] `ruff`/`mypy`/`pytest` проходят.

## Риск для отдельной проверки

Транслитерация кириллицы в `new_naive_username` — граничные случаи (пустая строка, только цифры,
только спецсимволы) должны давать валидный результат, а не падать. Добавить тесты именно на эти
случаи, не только на "счастливый путь".
