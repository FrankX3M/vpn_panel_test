# Интеграционное ТЗ — E2E "создать пользователя → конфиги валидны"

**Зависимости:** `01`–`08` (весь бэкенд, веб-UI не обязателен для этого сценария)
**Файлы:** `tests/integration/test_e2e_create_user.py`

## Задача

Один сквозной тест через `TestClient`, БЕЗ моков `render_*` (только `core.svc.control` мокается —
реальный `systemctl` в тестовом окружении может отсутствовать):

1. `POST /api/setup` с валидным `ServerConfig`.
2. `POST /api/users {"label": "Тест Юзер"}`.
3. Прочитать файл по `SINGBOX_CONFIG_PATH` (подменённому на `tmp_path` в фикстуре) →
   распарсить как JSON → убедиться, что `uuid` созданного `VlessAccount` присутствует в inbound.
4. Прочитать `CADDYFILE_PATH` → убедиться, что `username` созданного `NaiveAccount` присутствует
   в тексте файла.
5. `PATCH /api/users/{id} {"is_active": false}`.
6. Повторно прочитать оба файла → убедиться, что `uuid`/`username` этого юзера **исчезли** из
   конфигов (проверка, что отключение реально убирает доступ, а не только меняет флаг в БД).
7. Проверить, что мок `control()` был вызван для обоих сервисов на каждом из двух `apply()`
   (при создании и при `PATCH`).

## Почему это отдельное ТЗ, а не часть модульных

Каждое модульное ТЗ (01-08) тестирует свой контракт в изоляции с моками соседей — это ловит баги
внутри модуля, но не гарантирует, что **форматы данных на стыках совпадают** (например, что ключ,
который кладёт `02_key_generation`, называется точно так же, как ожидает `03_render_singbox`).
Именно такие баги на границе модулей чаще всего проходят мимо изолированных юнит-тестов.

## Критерии приёмки

- [ ] Тест проходит от начала до конца без единого мока `render_*`/`core.db`.
- [ ] Тест явно проверяет "отключение убирает из конфига", а не только "включение добавляет" —
      это самая частая асимметрия, которую забывают проверить.
